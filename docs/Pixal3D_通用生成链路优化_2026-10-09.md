# Pixal3D 通用生成链路优化（2026-10-09）

目标：让未来不同图片生成的模型普遍更可靠。本文记录通用链路代码修复，区别于此前对同一人物网格的减面、补法线和重新贴图实验。

后续验证与新增修复见 [第二轮链路优化记录](/D:/灵境造物/docs/Pixal3D_第二轮链路优化_2026-10-09.md)：本篇最终源码的单分支完整人物已成功；第二轮正在验证分块解码和 GGUF 加载内存改进。下文失败及“尚未验证”状态保留当时版本的真实记录。

## 实际入口

当前 `.env` 配置 `TRELLIS_PROVIDER=local_comfyui`、`TRELLIS_COMFY_ENABLED=true`。业务调用顺序为：

`backend/app/generation.py` → `services/trellis/app.py` → `services/trellis/workflow_6gb.json` → 本机 ComfyUI / Pixal3D-GGUF。

工作流采用 `Trellis2MeshWithVoxelAdvancedGenerator_GGUF` 从图片生成新几何和纹理体素，再交给 `Trellis2PostProcessAndUnWrapAndRasterizer_GGUF` 清理、重建网格、展开 UV、烘焙并导出 GLB。它没有调用此前固定网格纹理工作流的 `pipeline.postprocess_mesh`，所以前一轮修复不能自动覆盖全部导出逻辑。

初次基准沿用原模板 Q4_K_M / 512，但完整运行发现它调用了不存在的 512 纹理模型。业务模板已改用 Pixal3D 原生支持的 `1024_cascade`：512 粗形状 → 1024 精细形状 → 1024 纹理模型。原 guidance/区间、Q4、低显存、Smart UV、关闭自定义法线保持。基准通过实际服务的 `_build_comfy_prompt` 生成图，选择 medium 密度、1024 贴图；实际使用 16 步结构、每个形状阶段 16 步、20 步纹理、50 万面目标。内部模型分辨率与导出贴图尺寸是不同参数。没有把单个人物的相机距离、80 万面或 Q8 参数硬编码到业务模板。

## 本轮已安装的修复

安装位置：`E:\ComfyUI-Easy-Install\ComfyUI-Easy-Install\ComfyUI\custom_nodes\ComfyUI-Trellis2-GGUF`。

1. **通用导出坐标。** `MeshWithVoxel` 增加可选 `coordinate_system`，默认保留普通 TRELLIS 的 `z_up` 约定；实际 Pixal3D 解码结果标记 `y_up`，设备迁移保留标记。业务导出节点据此处理 PBR、顶点色和纯几何，避免把原生 Y-up 的 Pixal3D 再旋转。入口用 `getattr(mesh, 'coordinate_system', 'z_up')` 保留没有新字段的旧对象兼容性。模型解码前的投影、潜变量、体素和网格位置不做额外旋转。
2. **保护有效黑色材质。** 原补洞逻辑把 RGB 最大值小于 5 的表面像素视为缺失，可能抹掉有效黑色内容。新逻辑在体素采样时追加常数 1 的占用通道，只有没有体素支持的采样位置才进入内部补洞。UV 图块外部仍按原方法填充。没有依赖某一模型的头发颜色或区域规则。
3. **限制烘焙临时内存。** 原节点一次查询所有有效贴图像素的 BVH、取原三角面、插值并采样。现在按每批最多 262,144 个有效像素处理，沿用原 BVH 回投和 FlexGEMM 三线性采样数学。此处仍会保留整张光栅和贴图数组，不代表消除了全部显存需求，也未测出通用加速比例。
4. **修正业务默认生成分支。** 首个机器人任务在形状采样后抛出 `KeyError: tex_slat_flow_model_512`。实际 checkpoint 配置和已保存的 Pixal3D 原生实现只有 1024 纹理模型，原生完整生成支持 cascade；不能仅给不存在的 512 模型起别名、再用低分辨率潜变量冒充原生 1024 纹理流程。业务模板已改为 `1024_cascade`；管线对缺少 512 纹理模型的 512 带纹理请求增加 GPU 执行前明确报错，512 纯几何及配置中确实提供 512 纹理的模型仍可使用。
5. **投影使用实际阶段网格。** 原封装多处用 `coords.max()+1` 推算物理网格大小，但坐标只覆盖被占用的格子：去掉边缘体素就会改变其余体素的世界位置和图像投影。现在初始形状使用 `sparse_structure_resolution`，高分辨率 cascade 使用实际 `hr_resolution // 16`，纹理阶段使用返回的 `res // 16`，固定网格纹理使用编码分辨率。采样方法增加可选 `proj_grid_resolution`；省略时使用投影器配置的原生网格尺寸。没有改原生 `(x,-z,y)` 投影转换或固定网格透明前景取景。
6. **补洞后清空旧拓扑缓存。** 人物对照在补洞后的法线计算处发生原生 CUDA 崩溃。实际 CuMesh `init` 替换几何后仍保留旧顶点法线和顶点—面邻接缓存。补洞会改变面/顶点数量，旧缓存不再适用。现在 MeshLib 补洞结果重新送入 CuMesh 前调用其已有 `clear_cache()`。保留补洞和原法线选项，不靠删除验证或改变材质来掩盖故障。
7. **提前释放已结束阶段的局部持有者。** 原卸载函数清空管线属性并收集垃圾时，`run` 的 `ss_model`、形状投影模型等局部变量仍持有权重；不再使用的条件特征也一直留到函数结束。现在在原卸载位置之后释放对应局部引用，在纹理阶段前释放已卸载的形状投影器，在解码前释放完成采样的条件特征并执行已有清理方法。保留模型设置及采样/投影数学不变。实际低内存同进程峰值尚未在此最后改动后重测，不宣称内存分配失败已经普遍消除。

仅修改三个已存在源码文件：`nodes.py`、`trellis2_gguf/representations/mesh/base.py`、`trellis2_gguf/pipelines/trellis2_image_to_3d.py`。节点名、必填输入和返回类型保持不变。

同目录三个文件均保留 `.bak-before-general-pipeline-20261009` 备份。补丁：[本轮三文件差异](/D:/灵境造物/docs/Pixal3D_通用生成链路修复_20261009.patch)。插件升级可能覆盖这些本机修改，升级后需要重新核对，不能盲目覆盖新版本。
