## 结论及可信度

已确认两次 ComfyUI 崩溃时系统提交额度几乎耗尽；崩溃位置均为 NAF 条件特征的 GPU → CPU 拷贝。引擎退出后，平台显示断开连接，随后的重试显示连接被拒绝。这是同一次引擎故障造成的后续错误，不能继续当作普通网络错误处理。

不能把本次故障归结为“历史模型文件没有删除”。两次均发生在新启动的 ComfyUI 进程的第一个任务，当前引擎已退出，8188 无监听，显存空闲。生成结果保存到磁盘并不等于一直驻留在引擎显存中。

隔离实验额外复现了当前 PyTorch 运行时的大块 CPU 张量删除后，进程私有提交占用未立即回落、连续分配时继续增长的现象。这可能加重单次生成内的内存压力，但尚未证明具体的分配器缺陷，也不能将它认定为全部 13.8 GiB 引擎占用的来源。

之前成功、现在失败的区别，不能仅靠工作流名称解释。已经对比的主要参数和运行时版本一致；之前成功时的完整系统提交曲线没有留存，因此不能断言当时后台应用具体少了多少。

## 参数与数据规模核对

已核对成功与失败任务的主要配置：Q4_K_M、low_vram=true、keep_models_loaded=false、1024_cascade、主要采样步数、约 50 万面、1024 纹理；ComfyUI 0.34.0、PyTorch 2.8.0+cu128、cudaMallocAsync 等运行时设置相同。

任务 33–36 确认输入均为 RGBA 1024×1024。不能据此认定失败来自异常大的原始图片。

NAF dim=256、FP32。实际 shape1024 的 `naf_target_size=512`，对应 `[1,256,512,512]`，单张 CPU query 为 256 MiB；后续 tex1024 的目标才是 1024，对应 1 GiB。不要把纹理阶段的尺寸误当成本次崩溃形状阶段的尺寸。

代码中同时存在 CPU 卸载的模型和条件特征；低显存模式降低显存需求，也将一部分压力转移到系统内存。LR flow、LR 条件等在进入 HR 条件重建时仍可能被引用，且纹理条件投影器提前加载，值得后续做生命周期优化。

## 隔离实验

脚本：`scripts/diagnose_pixal_memory_20261022.py`。仅运行独立短进程，不启动 ComfyUI，不提交生成任务，不改生产环境变量。脚本有提交额度和可用物理内存保护。进程退出后，其占用随之释放。

1. CPU-only，三轮申请 256 MiB 张量、删除、GC；弱引用确认 Python 张量对象已销毁。进程私有提交仍逐轮增加约 264.5 MiB，短暂等待和小额后续分配未使它明显回落。
2. 临时设置 `MIMALLOC_PURGE_DELAY=0` 的独立进程仍复现，未构成修复。结果：`cpu-512-cudaMallocAsync-purge0.json`。
3. 临时禁止 arena 分配的独立进程仍复现。结果：`cpu-512-disallow-arena.json`。该报告生成时的 settings 未记录 shell 注入的变量；其余测试步骤由脚本记录。
4. 使用引擎相同的 cudaMallocAsync，三轮 GPU → CPU 256 MiB 拷贝后清理；GPU allocated/reserved 均回到 0，CPU 私有提交仍增长。结果：`copy-512-cudaMallocAsync-baseline.json`。
5. 最早的 `transfer-probe.json` 是 1 GiB 尺寸的探索实验，不能作为失败 shape 阶段尺寸的证据，也不是完整生成测试。

当前运行时诊断输出显示 mimalloc 2.2.3。仅凭版本号或上游发行说明，不能认定已经命中某个已知漏洞，更不能未经兼容性测试直接替换 torch DLL。

参考：[PyTorch 2.8 CPU 分配/释放实现](https://github.com/pytorch/pytorch/blob/v2.8.0/c10/core/impl/alloc_cpu.cpp)、[mimalloc 内存回收选项](https://github.com/microsoft/mimalloc#environment-options)。

## 后续修复优先级

1. 在生成前及关键阶段监测系统提交余量，明确区分引擎崩溃、连接拒绝与 GPU OOM；引擎退出后停止盲目重试。
2. 缩短阶段对象生命周期：HR 之前释放不再使用的 LR 模型及条件，将后续纹理模型改为需要时加载。需核对输出一致性，不能删掉仍有消费者的数据。
3. 单独定位 CPU 分配保留：用可替换的隔离环境验证分配器/运行时差异，再决定升级或进程隔离方案。
4. 在较低后台提交基线下，对原失败任务做完整生成和连续任务回归，记录提交峰值、显存峰值和结果质量。

本次完成了诊断及隔离测试；尚未修改生成链路、Windows 分页文件或用户后台应用，也没有宣称完整生成回归通过。
