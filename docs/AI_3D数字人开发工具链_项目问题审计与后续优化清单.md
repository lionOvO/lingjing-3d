## 一、项目定位

本项目的核心目标是：用户上传动漫角色或物品图片，经过图像分析、知识库检索、参数推荐、3D 模型生成和质量评估，最终得到可预览、下载和转换格式的 3D 模型。

核心业务链路为：

```text
上传图片
  -> 创建项目
  -> 创建生成任务
  -> 图像特征分析
  -> RAG 知识检索
  -> 3D 模型生成
  -> Mesh 质量评估
  -> 后处理
  -> 3D 预览 / 下载 / 格式转换
```

产品的差异化重点是：

1. 面向动漫角色和风格化物品的图片转 3D。
2. 通过多模态分析提取角色特征。
3. 通过 RAG 知识库推荐生成参数。
4. 通过智能体工作流串联分析、检索、生成、评估和重试。
5. 通过 WebSocket 或轮询向用户展示任务进度。

## 三、前端问题

### 3.1 页面与 PRD 的功能差距

| 优先级 | 问题 | 现状 | 建议 |
|---|---|---|---|
| P1 | 生成页参数项不完整 | PRD 要求输出格式、纹理分辨率、面数、拓扑类型、PBR 等；当前生成页主要提供 GLB、纹理、面数、模式和 PBR，拓扑类型等尚未完整暴露 | 明确当前支持的引擎能力，补齐可用参数，或在 PRD 中标注为后续功能 |
| P1 | 批量生成未形成完整流程 | PRD 将批量生成列为额外功能；当前页面主要围绕单张图片和单个任务 | 增加批量上传、任务分组、批量状态和失败重试设计 |
| P1 | 模型对比尚未实现 | PRD 要求支持 2-4 个模型并排比较；当前项目库和预览器以单模型为主 | 增加模型选择、同步视角、差异信息和结果导出 |
| P2 | 风格迁移尚未实现 | PRD 要求对 3D 模型应用不同风格材质；当前只有生成参数推荐相关入口 | 设计独立的风格/材质应用流程，明确是否重新生成纹理或仅调整材质 |
| P2 | 智能体调试界面不完整 | 任务详情页已展示分析与检索信息，但与 PRD 中完整 LangGraph 状态流转图仍有差距 | 将节点状态、输入输出、耗时、重试次数和错误原因结构化展示 |
| P2 | 实时日志体验不完整 | 当前重点是状态和阶段说明；PRD 期望实时日志 | 增加可折叠日志区、时间戳、日志等级和错误定位信息 |

### 3.2 页面结构与导航逻辑

| 优先级 | 问题 | 影响 | 建议 |
|---|---|---|---|
| P1 | 页面入口容易重复 | 首页、生成页、工作流页、任务详情页和模型预览器之间存在功能相邻的入口，用户可能重复进入同一任务链路 | 保留一条主路径：`首页 -> 生成 -> 工作流/任务详情 -> 预览器`；导航栏只保留稳定的一级入口 |
| P1 | 任务详情和工作流职责边界需要进一步明确 | 两者都展示任务进度和阶段信息，容易造成信息重复 | 工作流负责引导式步骤，任务详情负责完整状态、日志、参数和重试；完成后统一进入预览器 |
| P1 | 返回行为需要统一 | 不同页面的返回首页、返回项目、上一步和继续创建动作语义不完全一致 | 建立统一的返回规则，并保留任务 ID、项目 ID 和当前步骤参数 |
| P2 | 空状态和异常状态需要覆盖更多场景 | 网络失败、任务不存在、权限失效、模型文件缺失等场景需要分别处理 | 为每个页面定义加载中、空数据、无权限、请求失败和可恢复失败状态 |
| P2 | 移动端操作仍需系统验证 | 页面已有响应式规则，但复杂参数、工作流标签和 3D 控制在窄屏下风险较高 | 至少验证 320px、390px、768px 和桌面宽度，重点检查横向溢出和按钮遮挡 |

| 优先级 | 问题 | 建议 |
|---|---|---|

## 四、后端与智能体问题

### 4.1 核心业务与一致性

| 优先级 | 问题 | 风险 | 建议 |
|---|---|---|---|
| P0 | 需要确认鉴权是否覆盖所有项目、任务和模型接口 | 若仅依赖前端传入 `user_id` 或资源 ID，可能造成越权读取或操作 | 所有资源查询、下载、删除、重试和转换接口都必须从当前登录用户推导权限 |
| P1 | 任务状态机需要严格约束 | 生成、评估、重试、取消和完成可能产生非法状态跳转 | 使用明确状态机，限制可转移状态，记录每次状态变更 |
| P1 | 重试与幂等需要统一 | 网络重试可能重复创建项目、任务或重复执行生成 | 使用幂等键、任务唯一约束和可重入 worker 设计 |
| P1 | 取消任务的实际语义需要明确 | API 取消记录不等于 GPU/Celery 任务已停止 | 明确取消信号、worker 响应、资源回收和最终状态 |
| P1 | WebSocket 与轮询状态一致性需要验证 | 连接断开、重复消息或消息乱序可能让页面显示旧状态 | 以服务端持久化状态为准，消息带版本号或时间戳，前端丢弃旧事件 |
| P2 | 项目更新接口与文档方法可能存在差异 | PRD 使用 PUT，当前前端曾使用 PATCH 更新项目 | 统一 API 契约，补充 OpenAPI 和前端类型定义 |

### 4.2 AI、RAG 与生成链路

| 优先级 | 问题 | 风险 | 建议 |
|---|---|---|---|
| P1 | 外部模型服务失败时的降级策略需要验证 | Qwen、TRELLIS、Hugging Face 或本地模型失败会中断主流程 | 为分析、检索、生成和评估分别定义超时、重试、降级和错误码 |
| P1 | 生成参数来源需要可追溯 | 参数可能来自用户选择、RAG 推荐或重试调整，出现结果问题时难以定位 | 保存原始参数、推荐参数、最终参数、调整原因和每次重试版本 |
| P1 | RAG 推荐结果需要反馈闭环 | PRD 目标包含持续学习和推荐采纳率，但需要真实反馈数据支撑 | 记录推荐展示、采纳、修改、生成质量和用户反馈，并定期评估推荐效果 |
| P1 | 质量评估规则需要修正和扩展 | 仅依赖少量 Mesh 检查无法代表角色还原度、材质质量和可用性 | 将几何、纹理、风格一致性、面数、文件完整性拆分评分，并保存检查明细 |
| P1 | 质量检查代码需要避免无效校验 | 类似“列表长度等于自身”的恒真检查不能发现退化面等问题 | 使用 trimesh 或其他可靠几何算法检查退化面、自交、法线、UV、材质和纹理引用 |
| P2 | Milvus schema 与 embedding 模型维度需要固定 | 不同 embedding 维度或字段结构不一致会导致检索失败 | 把集合 schema、模型版本和维度写入配置与迁移脚本，启动时检查 |
| P2 | 知识库数据质量需要治理 | 预置数据不等于可持续的生产知识库 | 增加来源、版本、审核状态、适用范围、成功样本和过期策略 |
| P2 | 模型文件和纹理存储生命周期需要明确 | 大文件长期堆积会增加成本，公开 URL 也可能产生权限问题 | 使用对象存储、短期签名 URL、清理任务和项目级访问控制 |

## 五、部署与配置问题

| 优先级 | 问题 | 建议 |
|---|---|---|
| P0 | 生产环境密钥不能使用示例值或明文提交 | 使用环境变量、密钥管理服务和最小权限账号；检查 `.env`、日志和镜像层 |
| P0 | Docker Compose 的 GPU、依赖启动顺序和健康检查需要实测 | 对 frontend、backend、worker、Redis、MySQL、Milvus、MinIO 和生成服务逐项验证 |

| P1 | 开发环境与生产环境配置可能漂移 | 本地 URL、容器服务名、CORS、文件路径和模型路径不同 | 分离 `.env.example`、开发配置、测试配置和生产配置 |
| P1 | GPU 资源限制和并发策略需要明确 | 多任务同时生成可能造成显存溢出和任务饥饿 | 设置队列并发、显存门控、超时、任务优先级和资源监控 |
| P2 | 数据库迁移和初始化流程需要标准化 | 依赖现有数据库文件或手工初始化会影响部署复现 | 使用迁移工具、种子脚本和可重复初始化流程 |
| P2 | 日志和链路追踪需要统一 | 多服务异步执行时难以串联一次生成任务的全过程 | 所有请求、任务、worker 和模型调用携带 `request_id` / `task_id`，输出结构化日志 |

## 十、维护规则

1. 新增页面前先确认它是否能复用现有页面，避免重复入口。
2. 新增状态颜色前先使用语义 token，不直接写绿色或其他硬编码颜色。
3. 修改主页主题时同步检查所有二级页面，保证主页仍是视觉基准。
4. 产品文档中的“规划功能”必须标记实现状态：已实现、部分实现或未开始。
5. 每次核心流程修改至少执行一次前端构建、后端测试和主链路手工验证。
6. 任何涉及权限、任务状态、模型文件和外部模型调用的修改，都应补充对应测试。
